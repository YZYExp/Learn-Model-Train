# 部署实践：怎样设计可信的推理压测

「模型每秒多少 token」不是完整的性能结论。用户等待首字出现、后续生成和任务完成；运营者关心目标成功率下，多少请求能在时限内完成、每次成功花多少钱。这里的数字均为假设，**本书环境没有运行 GPU 服务压测**。

## 固定比较合同

比较部署方案时记录权重与量化版本、tokenizer 和聊天模板、system prompt、工具定义、输入集合、输出上限、采样参数、请求到达方式及可用硬件。记录引擎版本、驱动、GPU、网络拓扑、启动参数和模型哈希。量化改变权重时要同时验证质量；引擎对 EOS 或 tokenizer 的处理不同，输出 token 数也可能变化。

构造代表性请求集：例如 60% 为 2k 输入/256 输出、30% 为 8k/512、10% 为 32k/1024。**这只是教学分布，实际分布来自业务统计。**混合平均值可能掩盖长请求的尾延迟，应分别报告各桶和整体的样本数、成功率及延迟分位数；系统提示和工具 schema 也要计入 token。

## 四种时间，两种吞吐

- **TTFT**：客户端发出请求到收到第一个生成 token；包含网络、排队和 prefill。要明确第一个事件的定义。服务端 prefill 时间不是客户端 TTFT。
- **后续 token 延迟**：相邻生成 token 间隔；代理把多个 token 打包到一个事件时，客户端观测值会受到影响。
- **端到端延迟**：提交到结束，包括排队、生成和网络；HTTP 成功还需结合生成终止原因判断。
- **排队等待**：服务端接收至调度开始的时间，应分别观察长短请求与 p50/p95/p99。
- **输出 token/s**：整个观测区间输出 token 总量除以区间长度，不能把时间窗口不同的每请求速度简单相加。
- **goodput**：可定义为每秒既成功又满足预设延迟及质量门槛的请求数；分子、分母与门槛必须明确。

vLLM 提供 Prometheus 指标，其名称和定义可能随版本变化；应用端 TTFT 仍需客户端测量。[vLLM 指标](https://docs.vllm.ai/en/latest/design/metrics/)

## 闭环、开环与缓存

闭环压测固定客户端数，每个客户端等响应后才发下一条；服务变慢时请求产生速度也下降。开环压测按预设到达率发送，较易暴露队列堆积，但需要设置超时和停止条件，避免无界积压。两种方法都要记录实际到达率，不能只写「并发 16」。

从低负载逐步增加请求率；每档包含预热、稳定观察和排空。记录成功率、超时、队列、TTFT、端到端时延、KV 缓存和 GPU 利用情况。按长度分桶报告；p99 基于很少请求时会大幅波动。发生 OOM、错误率超标或 p95 超过门槛时停止加压。分别测试冷启动、模型热启动、前缀缓存冷和缓存热。

前缀缓存需要可复用的相同 token 前缀；模板、工具 schema 或 tokenizer 变化都可能影响命中。对照冷缓存和预热后同分布负载，记录命中率、缓存占用和 TTFT；租户隔离需按引擎及网关配置核验。[vLLM 前缀缓存](https://docs.vllm.ai/en/latest/design/prefix_caching/)

## 成本与质量一起看

假设方案 A 每小时 4 美元，在时限内成功处理 800 个任务，服务成本为 `4 / 800 = 0.005` 美元/成功任务；方案 B 每小时 3 美元，只成功 450 个，成本约 `0.0067` 美元/成功任务。此例忽略闲置、重试和网关成本，只说明为什么不能单看每小时价格。

在代码 Agent 场景，格式合法率只衡量接口；还要用隔离测试与副作用检查评估实际任务。比较量化前后结果时保存每题成功、失败原因、token 和延迟，按同一任务配对分析回归。最终归档硬件、软件、模型与数据版本、负载分布、采样、缓存状态、原始结果、成本和失败样本；不要只保存一张最高吞吐截图。
